# AGENTS.md — инструкция для кодинг-агента

Ты строишь целиком, от пустого репозитория до работающего стенда, сервис «Приём документов соискателей» для кадрового агентства. Решение пойдёт в прод: персональные данные (паспорта, СНИЛС, ИНН, миграционные документы) не должны уходить за периметр.

Работаешь автономно по `docs/TASKS.md`, фаза за фазой. Спецификация лежит в `docs/spec/`. Если спецификация чего-то не покрывает, принимаешь разумное решение, записываешь его в `docs/decisions.md` (черновик) и идёшь дальше. Человека спрашиваешь только о необратимом: удалить данные, переписать историю git, выложить что-то наружу.

## 1. Что читать и в каком порядке

1. `docs/spec/01-product.md` — что строим, приоритеты P0/P1/P2, условия допуска Д1–Д12.
2. `docs/TASKS.md` — фазы, задачи, гейты. Это твой план.
3. Остальные файлы `docs/spec/` — по мере того, как фаза их требует:
   - `02-architecture.md` — сервисы, сети, стек, структура репозитория;
   - `03-data-model.md` — таблицы, статусы, очередь;
   - `04-api.md` — контракт API и тексты ошибок;
   - `05-pipeline.md` — разбор документа: проходы, сверка, уверенность;
   - `06-documents.md` — восемь видов документов, правила, алгоритмы, тестовые векторы;
   - `07-auth-security.md` — Keycloak, BFF, роли и группы, соискатель, периметр;
   - `08-frontend.md` — два интерфейса;
   - `09-model-gateway.md` — шлюз модели, Qwen3.8, olmOCR, сбои;
   - `10-eval-ops.md` — оценка качества, журнал, эксплуатация, сценарий защиты.
4. `registry/documents.yaml` — реестр документов и правил, единый источник истины.
5. `prompts/` — промпты модели, версионируются.
6. `docs/templates/` — шаблоны обязательных документов кейса (п. 5.5).

## 2. Непреложные правила

Нарушение любого пункта снимает команду с конкурса или обнуляет блок баллов.

1. **Только реальный разбор.** Поля читаются моделью из пикселей и текста файла. Запрещено:
   - выводить данные из имени файла, порядка загрузки или размера;
   - зашивать значения из открытого набора в код, промпты или примеры;
   - ставить статус «готово» без вызова модели.

   Исходное имя файла хранится только для показа человеку. В пайплайн оно не передаётся: пайплайн получает байты и UUID.
2. **Никаких выдуманных данных.** Если модель не ответила, ответила не по схеме или с `finish_reason != "stop"`, документ получает честный статус ошибки с причиной и возможностью повторить. Частичный результат не выдаётся за готовый. В коде приложения нет «фейкового провайдера»: моки модели живут только в `tests/` (respx).
3. **Сервер решает всё.** Любая проверка, от которой зависит результат (тип и размер файла, дубликат, согласие, права, статус), выполняется на бэкенде. Проверки во фронтенде — только подсказка.
4. **Всё в постоянном хранилище.** Сущности, события, очередь и журнал живут в PostgreSQL, файлы — в S3 (SeaweedFS). Состояние в памяти процесса для бизнес-данных запрещено.
5. **Фон и устойчивость.** Приём отвечает мгновенно. Разбор идёт в воркере через очередь `jobs` в PostgreSQL. Файл и задача пишутся одной транзакцией. Убитый воркер не теряет работу.
6. **Закрытость.** Любой маршрут `/api/operator/*` и любой файл без валидной сессии отдают 401. Объект чужой группы отдаёт 404. На это есть автотест, который сам перечисляет все маршруты приложения.
7. **Все вызовы моделей — только через `backend/app/llm/`.** Адрес, модель и ключ берутся из переменных окружения. В других модулях нет ни одного HTTP-вызова к модели.
8. **Секреты — только в `.env`**, который в `.gitignore`. В репозитории лежит `.env.example` без значений. Перед каждым коммитом запускается gitleaks (pre-commit). Ключи, пароли, IP-адреса и логины серверов не пишутся ни в код, ни в документацию, ни в сообщения коммитов.
9. **Никаких внешних сервисов для персональных данных.** Модель: Qwen3.8 на `llm.ilons.ru` — локальная модель в контуре, развёрнутая сотрудником. OCR: olmOCR на `ocr.ilons.ru`. Запасная модель — vLLM на нашей A10. GigaChat, OpenAI, облачные OCR, внешние CDN, шрифты и аналитика не используются: фронтенд собирается без внешних ресурсов.
10. **Тексты для людей — по-русски.** Пользователь не видит технических кодов, англоязычных трассировок и стектрейсов. Только понятный текст, совет, что делать, и короткий код обращения в поддержку (request_id).

## 3. Порядок работы

- Иди строго по фазам `docs/TASKS.md`. Не начинай следующую фазу, пока не пройден гейт текущей.
- Сначала один документ (паспорт РФ) проходит весь путь на настоящей модели: загрузка → очередь → разбор → карточка оператора. Только потом расширяйся на восемь видов документов.
- Каждая задача — маленький законченный шаг: код, тест, коммит.
- После каждой правки промпта или логики разбора запускай `make eval` и клади отчёт в `eval/reports/`.
- Отмечай выполненное в `docs/TASKS.md` (`[x]`) и коммить вместе с кодом.
- Если что-то не работает больше 30 минут, упрости, запиши ограничение в `docs/limitations.md` и двигайся дальше. Обязательный объём (P0) важнее бонусов.

## 4. Git

- Коммит — маленький осмысленный шаг. Сообщение на русском, в повелительном наклонении, о том, что изменилось: «Добавить проверку контрольной суммы ИНН». За работу должно получиться не меньше 30 коммитов.
- Автора коммита не меняй и не подделывай: коммить под той git-идентичностью, которая настроена на машине. Кейс требует коммитов от каждого участника. Поэтому каждый человек запускает тебя на своих модулях (карта владения в `docs/TASKS.md`) под своей идентичностью или сам коммитит проверенный им код.
- `.gitignore` с первого коммита: `.env`, `node_modules/`, `.venv/`, `dist/`, `__pycache__/`, `data/`, `*.dump`, `*.zip`, `eval/cache/`, файлы IDE.
- Не коммить данные открытого набора, если в них могут быть реальные персональные данные. По умолчанию они лежат в `data/` (игнорируется).

## 5. Определение готовности (DoD) любой задачи

- Код написан, проходит линтеры (`ruff`, `mypy --strict` для `app/registry`, `app/llm` и `app/pipeline`; `eslint` и `tsc` для фронтенда).
- Есть тест на логику: обязательно для валидаторов, контрольных сумм, МЧЗ, дат, приёма файлов, прав доступа, очереди и шлюза модели.
- Значимое действие пишется в журнал аудита (`audit_events`) с русским текстом.
- Ошибка пользователю — по-русски, через каталог сообщений `backend/app/messages.py`.
- `docker compose up -d --build` с чистого `.env` поднимает систему, функция работает через интерфейс.

## 6. Как проверять себя

- `make test` — юнит- и интеграционные тесты (интеграционные используют PostgreSQL из compose-профиля `test`).
- `make e2e-smoke` — скрипт: создать заявку, загрузить файл, дождаться финального статуса, войти оператором через Keycloak (тестовый пользователь), открыть карточку, проверить 401 без cookie.
- `make eval` — качество разбора на открытом наборе (dev/holdout) и искажённых копиях.
- `make restart-drill` — поставить 20 файлов, убить воркер посреди разбора, поднять снова и проверить, что все 20 дошли до финального статуса.

## 7. Чего не делать

- Не тащить тяжёлые платформы: Celery, Redis, Kafka, LiteLLM, LangChain, Instructor, готовые IDP-системы. Свой тонкий код проще объяснить и поправить за 10 минут.
- Не использовать библиотеки с AGPL/GPL (PyMuPDF, mrz). Для PDF — pypdfium2, МЧЗ разбираем своим парсером.
- Не использовать presigned URL для файлов: файлы отдаёт только API после проверки сессии и группы.
- Не включать thinking у Qwen и не ставить регулярки в JSON-схему декодера (см. `09-model-gateway.md`).
- Не писать персональные данные, изображения и ответы модели в технические логи.
- Не открывать наружу порты, кроме 80/443 у Caddy. Отладочные интерфейсы (Mailpit, админка Keycloak) — только на 127.0.0.1, через SSH-туннель.

## 8. Завершение

Когда все гейты P0 и P1 пройдены:

1. Заполни документы из `docs/templates/` и положи их на свои места: `README.md`, `docs/architecture.md`, `docs/decisions.md`, `docs/local-model.md`, `docs/limitations.md`, `docs/ai-usage.md`, `docs/how-to-change.md`.
2. Пройди README буквально, на чистом клоне: `git clone` → `.env` → `docker compose up`.
3. Финальная фаза 6 из `docs/TASKS.md` выполняется только по прямой просьбе человека: передаточные документы `docs/handoff/backend.md` и `docs/handoff/frontend.md`.
