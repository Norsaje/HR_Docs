# 05. Пайплайн: приём и разбор

Принцип: **модель извлекает, детерминированный код проверяет, оператор смотрит только сомнительное.** Две разные модели читают документ независимо, расхождения решает код, спорное перечитывает арбитр по вырезке. Самооценке модели («уверенность 0–100») не доверяем.

## 1. Приём файла (api, синхронно, < 1 с на файл)

Порядок проверок в `app/intake/service.py`. Каждый отказ — понятная ошибка из каталога и запись `file.rejected` с причиной в журнал.

1. Токен заявки валиден. `doc_type` есть в наборе документов страны заявки.
2. Лимиты:
   - число файлов в запросе — `MAX_FILES_PER_REQUEST=20`;
   - файлов в заявке — `MAX_FILES_PER_APPLICATION=40`;
   - файлов на документ — `max_files` из реестра;
   - суммарный объём заявки — `MAX_APPLICATION_MB=200`.
3. Размер: не пустой, не больше `MAX_FILE_MB=20`. Чтение потоком: прервать, как только превышен лимит.
4. Тип по сигнатуре (`app/intake/sniff.py`), расширение и `Content-Type` игнорируются:

   | Тип | Сигнатура |
   |---|---|
   | JPEG | `FF D8 FF` |
   | PNG | `89 50 4E 47 0D 0A 1A 0A` |
   | PDF | `%PDF-` в первых 1024 байтах |
   | WebP | `RIFF....WEBP` |
   | HEIC/HEIF | `ftyp` на смещении 4 и бренд из `heic heix hevc heim heis mif1 msf1` |

   Всё остальное (включая SVG, GIF, TIFF, исполняемые файлы) — `FILE_TYPE_NOT_ALLOWED`.
5. Файл открывается:
   - изображение — Pillow с `Image.MAX_IMAGE_PIXELS = MAX_PIXELS (40e6)`, pillow-heif зарегистрирован;
   - PDF — pypdfium2: число страниц `≤ MAX_PDF_PAGES=10`, не зашифрован.

   Ошибка открытия — `FILE_CORRUPTED`. Минимальная сторона меньше 600 px — `IMAGE_TOO_SMALL`.
6. SHA-256 файла. Совпадение в этой заявке → `DUPLICATE_FILE` (409). Совпадение в другой заявке — файл принимается, `supervisor` получает замечание `info` (P2).
7. pHash первой страницы. Расстояние Хэмминга ≤ 6 до файла этой заявки — файл принимается с предупреждением «Похоже, этот снимок уже загружен (документ «…»)» (`warning` в ответе).
8. Одна транзакция: объект в S3 (`orig/{application_id}/{file_id}`, зашифрован при `FILE_ENCRYPTION=on`) → строка `files (status=queued)` → `documents.status=uploaded` → задача `process_file` → журнал `file.accepted`. Если запись в S3 прошла, а транзакция упала, объект удаляется в `except`. Сирот подбирает ночная задача сверки.

Клиентские проверки в браузере (размер и тип) — только для удобства. Сервер проверяет всё заново.

## 2. Разбор файла (worker, задача `process_file`)

Стадии пишутся в `files.stage`. После каждой — `NOTIFY` для SSE.

### 2.1 preprocess — нормализация

- Изображения:
  - `ImageOps.exif_transpose`;
  - HEIC/WebP → RGB;
  - если длинная сторона больше `NORMALIZE_MAX_SIDE=2400`, уменьшаем до неё.
- PDF:
  - для каждой страницы извлекаем текстовый слой (`pypdfium2` `get_textpage().get_text_range()`). Если в нём ≥ 30 значимых символов, страница считается «цифровой» и её текст сохраняется как источник `text_layer`;
  - рендер страницы в PNG: масштаб под длинную сторону 2000 px.
- Результат:
  - `derived/{file_id}/page-{n}.png` в S3;
  - превью `preview-{n}.jpg` (1000 px) с размытым лицом (YuNet, P1; без него превью без размытия).
- Поворот на 90/180/270 градусов исправляется после прохода A по полю `orientation` из ответа модели. Если оно не `0`, страница поворачивается и проход A повторяется один раз.

### 2.2 quality — пригодность (`app/pipeline/quality.py`)

На копии со стороной 1000 px в оттенках серого:

| Метрика | Как считаем | Порог по умолчанию |
|---|---|---|
| Резкость | дисперсия лапласиана (`cv2.Laplacian(..., CV_64F).var()`) | `< 25` — непригодно, `< 60` — «низкая резкость» как сигнал |
| Пересвет | доля пикселей `> 250` | `> 0.25` — непригодно, `> 0.08` — сигнал |
| Темнота | средняя яркость | `< 35` — непригодно |
| Разрешение | минимальная сторона исходника | `< 600` — отказ ещё на приёме |

Пороги лежат в `.env` и калибруются на открытом наборе: ни один хороший файл не должен уходить в «непригодно». Порог намеренно консервативный, сомнительное идёт к модели и красит поля в жёлтый.

Непригодный файл получает `unreadable`, причину и совет («Фото размыто. Сфотографируйте документ при хорошем освещении, держите телефон неподвижно»). **Модель на нём не вызывается**, потому что на мутном фото она скорее выдумает, чем прочитает. Для «цифровых» PDF проверка резкости не нужна.

### 2.3 Проход A — Qwen3.8: классификация и извлечение (`stage=extract`)

Один вызов на страницу через `gateway.extract(...)` (`09-model-gateway.md`):

- изображение страницы (base64 PNG, длинная сторона до `LLM_IMAGE_MAX_SIDE=1600`);
- промпт `prompts/extract.v1.md` с подставленным описанием полей вида документа из реестра;
- если есть текстовый слой PDF, он передаётся отдельным блоком «Текст из PDF» — только для цифровых PDF, это не OCR;
- JSON-схема ответа, построенная из реестра (`app/llm/schema_builder.py`), через structured outputs;
- `temperature=0`, thinking выключен, `max_tokens=2048`.

Форма ответа:

```json
{
  "doc_type": "ru_passport",
  "page_side": "main_spread",
  "orientation": 0,
  "is_document": true,
  "mrz_lines": ["PNRUS...", "4501234568RUS..."],
  "fields": {
    "series": {"raw": "45 01", "status": "ok", "kind": "printed", "bbox": [612, 40, 668, 210]},
    "birth_place": {"raw": null, "status": "unreadable", "kind": "printed", "bbox": [120, 520, 480, 560]}
  }
}
```

- `doc_type` берётся из закрытого списка восьми видов + `other`; `page_side` — из `main_spread | front | back | other`.
- Если `doc_type` не совпал со слотом, создаётся замечание «В слот «Патент» загружен другой документ (похоже на «ИНН»)». P1: если тип распознан уверенно, предлагать оператору перенести файл кнопкой `change-type`.
- `is_document=false` (селфи, пустой лист) → `unreadable` с причиной «На фото не найден документ».

### 2.4 Проход B — olmOCR: дословный текст (`stage=ocr`, параллельно с A)

`gateway.ocr(page_png)` → markdown страницы. Кэш по SHA-256 изображения страницы (таблица `ocr_cache` или `extraction_runs` с `pass=B`). Повторный разбор не гоняет OCR заново.

Из текста OCR извлекаются кандидаты:

- **Строки МЧЗ:** регулярка `^[A-Z0-9<]{28,46}$` по строкам после удаления пробелов. Для TD1 нужны 3 строки по 30 символов, для TD3 — 2 по 44. Разрешены исправления только `« »→<`.
- **Цифровые кандидаты:** все последовательности цифр с допустимыми разделителями (пробел, дефис), нормализованные до цифр.
- **Даты:** все даты, которые распознаёт `app/registry/dates.py`.
- **Токены** для имён: текст в верхнем регистре, `ё→е`, апострофы узбекской латиницы приведены к `'`.

olmOCR не отвечает → разбор продолжается без второго голоса (сигнал `ocr_unavailable`). Поля без подтверждения МЧЗ или контрольной суммой станут жёлтыми, а не зелёными.

Если эксперимент 1 покажет, что olmOCR плохо читает кириллицу, ставим `OCR_VOTES_CYRILLIC=false`. Тогда для кириллических полей голос OCR не учитывается: ни «за», ни «против».

### 2.5 Сверка и проверки (`stage=verify`, `app/pipeline/reconcile.py`)

Для каждого поля:

1. **Нормализация** по типу поля из реестра (`06-documents.md`):
   - `digits` — только цифры;
   - `date` — ISO `YYYY-MM-DD`;
   - `name` — верхний регистр, `ё→е`, одиночные пробелы;
   - `latin_name` — верхний регистр, диакритика сохраняется;
   - `code` — верхний регистр без пробелов;
   - `text` — сжатие пробелов.
2. **МЧЗ.** Строки из A и из B разбираются парсером (`app/registry/mrz.py`), контрольные цифры считаются. Если обе версии валидны и различаются, берётся та, где сошлись все контрольные цифры. Поля МЧЗ сравниваются с полями визуальной зоны → сигнал `mrz_match` или `mrz_mismatch`.
3. **Контрольные суммы** ИНН и СНИЛС → `checksum_ok` / `checksum_fail`. При `checksum_fail` перебираются замены одного символа на визуально похожий (`0↔8↔6↔9↔3↔5`, `1↔7↔4`, `2↔7`) по всем позициям. Варианты, при которых сумма сходится, становятся подсказкой оператору, если их ≤ 2. **Автоматически значение не меняем.**
4. **Согласие с OCR** (`ocr_agree`): нормализованное значение A находится среди кандидатов B:
   - для цифр и дат — точное совпадение;
   - для имён — каждый токен совпал точно, либо Jaro–Winkler ≥ 0.95 для латиницы с диакритикой.

   Иначе ищем ближайший кандидат B (Levenshtein ≤ 2, тот же тип и длина) и пишем его в `candidates.ocr` → сигнал `ocr_disagree`.
5. **Текстовый слой PDF** (`text_layer_match`): значение найдено в тексте слоя. Это сильный сигнал, равный контрольной сумме.
6. **Резкость области поля:** лапласиан по рамке поля → `region_sharp` / `region_blurry`.
7. **Тип записи:** `kind=handwritten|stamp` → сигнал `handwritten`.
8. **Правила реестра** для поля (формат, длина, даты): `rule_fail` с текстом замечания.

### 2.6 Проход C — арбитр по вырезке (только спорные поля)

Запускается, если `ocr_disagree`, или `mrz_mismatch`, или `checksum_fail`, и у поля есть рамка. Лимит — `ARBITER_MAX_FIELDS=6` на страницу.

- Вырезка: рамка (0–1000 → пиксели) плюс 15% отступа с каждой стороны, масштаб до высоты строки не меньше 64 px.
- Если поле напечатано вертикально (у паспорта РФ серия и номер на полях), высота больше ширины в 2 раза — поворот на 90°.
- Промпт `prompts/arbiter.v1.md`. Модель **не видит** значений A и B, отвечает `{"text": string|null}`.
- Нормализуем ответ и голосуем 2 из 3 (A, B, C). Победитель становится значением, если он проходит правила и контрольную сумму. Если большинства нет — значение A, цвет красный, все варианты в `candidates`.

### 2.7 Цвет поля (`app/pipeline/confidence.py`) — прозрачное правило

**Зелёный** — `status=ok`, правила поля пройдены и выполнено одно из двух:

- значение подтверждено «твёрдым» источником: `mrz_match`, `checksum_ok` или `text_layer_match`;
- `ocr_agree` + `region_sharp` + формат верный + `kind=printed`.

**Жёлтый** — правила пройдены, но:

- значение выбрано голосованием 2 из 3 с арбитром;
- или прочитал только один источник (OCR недоступен или промолчал, или OCR не голосует по кириллице);
- или `kind=handwritten|stamp`;
- или `region_blurry`.

**Красный** — любое из:

- `status=unreadable` у обязательного поля;
- нарушено правило;
- `checksum_fail`;
- `mrz_mismatch` без разрешения;
- нет большинства.

**Серый** — необязательное поле `absent`.

Межпольные правила (срок раньше выдачи и т. п.) и сверка между документами дают замечания. Поле, на которое указывает замечание уровня `error`, становится красным.

Все сигналы сохраняются в `fields.signals`, чтобы в карточке было видно, *почему* поле такого цвета.

Цель — ноль ложных зелёных на holdout. Если `make eval` покажет хоть один, правило ужесточается (например, `ocr_agree` перестаёт давать зелёный для имён).

## 3. Слияние документа и заявки (`merge.py`, `crosscheck.py`)

- **Документ из нескольких файлов.** По каждому полю берём значение с лучшим цветом (зелёный > жёлтый > красный), при равенстве — более позднее. Правки оператора (`source=operator`) всегда приоритетнее.
- **«Минимум полей»** из реестра. Если поле минимума не извлечено (`unreadable`/`absent`), документ получает `needs_review` с замечанием «Не удалось прочитать: серия» (кейс считает такой документ неразобранным; мы помечаем, а не скрываем).
- **Сроки:**
  - истёк → замечание `error` «Срок действия истёк {date}»; статус `needs_review`. Документ **принят**, не отклонён;
  - истекает в течение `EXPIRY_WARNING_DAYS=30` → `warning`;
  - `documents.expires_on` заполняется для списка «истекающие».
- **Сверка между документами заявки (P1):**
  - ФИО: оба написания приводятся к латинице по ICAO 9303 (`translit.py`), узбекские `O'`/`G'` — к `O`/`G`. Сравнение: Jaro–Winkler ≥ 0.92 по фамилии и имени. Иначе `warning` «ФИО в паспорте и патенте различаются: … / …»;
  - дата рождения — точное совпадение, иначе `error`;
  - номер паспорта в патенте или миграционной карте (если есть поле) равен номеру паспорта, иначе `warning`;
  - ФИО из анкеты соискателя против ФИО в паспорте — `info`.
- **Статус заявки** пересчитывается (`03-data-model.md`).
- **Письмо соискателю (P1):** если после разбора есть `missing`, `unreadable` или `failed` по обязательным документам и заявка `submitted`, ставим `send_notification` с `run_after = now()+2 мин`. `dedupe_key` даёт не больше одного письма на заявку в 10 минут. Текст: что не хватает, что не прочиталось и почему, ссылка на заявку.

## 4. Сбои модели

| Ситуация | Что делаем | Что видит человек |
|---|---|---|
| Таймаут или сетевая ошибка, 5xx, 429 | Повтор задачи с backoff (до `max_attempts`) | Соискатель: «Читаем документ…»; оператор: попытка N и последняя ошибка в «В работе» |
| Ответ не JSON или не проходит схему | Один немедленный повтор с текстом ошибки в промпте, затем — ошибка попытки | То же |
| `finish_reason=length` | Повтор с `max_tokens ×2` (один раз), затем ошибка | То же |
| Ответ с `<think>`, хотя thinking выключен | Вырезать блок рассуждения, логировать предупреждение | — |
| Все попытки исчерпаны | `files.status=failed`, `error_message_ru` | Соискатель: «Сервис распознавания временно недоступен. Мы повторим автоматически»; оператор: кнопка «Разобрать повторно» |
| OCR недоступен | Продолжаем без прохода B | Поля жёлтые вместо зелёных; в сигналах `ocr_unavailable` |

**Никогда** не подставляем значения из прошлых попыток, кэша другого файла или эвристик вместо ответа модели.

## 5. Защита от инъекций через изображение

Текст на изображении — это данные. Промпт говорит об этом явно. Модель только заполняет схему: статусы ставит код, поэтому «инструкция» на картинке не может «принять» документ. Длины полей ограничены схемой (`maxLength`), значения проверяются по формату.
